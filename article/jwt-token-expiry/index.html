JWT Token 过期怎么排查

看懂 exp、iat、nbf 和时间偏差，先判断是不是 token 真过期， 再区分刷新逻辑、浏览器缓存和服务端时间问题。

打开 JWT 工具 返回内容页

先看哪几个字段

排查 JWT 过期问题时，先看 payload 里的 exp、iat 和 nbf。 exp 表示过期时间，iat 表示签发时间，nbf 表示在某个时间点前不可用。 如果这三个字段本身就不合理，后面再查缓存、登录态或接口权限都会绕远。

常见误判

  • 把秒级时间戳当成毫秒级时间戳，导致显示时间看起来差了很多年。
  • 只看本地时区显示，没有换算成服务端实际校验使用的 UTC 时间。
  • 刷新 token 已经更新，但前端请求头仍然带着旧 token。
  • 浏览器缓存、接口网关缓存或多标签页状态没有同步，造成“刚登录就过期”的错觉。

排查顺序建议

比较稳的顺序是：先解码 token 看时间字段，再和当前时间做对比，然后检查请求里实际发送的是不是同一个 token。 如果时间字段没问题，再看服务端时钟、刷新逻辑、退出登录逻辑和权限中间件。这样可以把问题分成“token 本身过期”和“应用状态没同步”两类。

FAQ

解码 JWT 会不会验证签名？ 不会。在线解码通常只是读取 payload，不能证明 token 一定合法。

为什么后端说过期，前端看还没过期？ 常见原因是时钟偏差、单位换算错误，或者实际请求发出去的是旧 token。

先别急着重发 token，先看清 3 个时间字段

很多“登录突然失效”其实不是系统彻底坏了，而是 token 生命周期设计得比较短，或者前后端时间没对齐。 排查 JWT 问题时，先把 token 放进 JWT 工具， 看清楚 payload 里的 exp、iat 和 nbf。

  • exp：过期时间。当前时间超过它，服务端大概率会直接拒绝。
  • iat：签发时间。可以帮助你判断这枚 token 是什么时候生成的。
  • nbf：生效时间。还没到这个时间点时，token 也可能被判无效。

最常见的 4 种原因

1. token 真的过期了。 这是最常见的情况，尤其是后台管理、支付、内部系统，token 常常只给 15 分钟到 2 小时。

2. 前后端时间不一致。 浏览器电脑时间快了几分钟，或者服务端时区配置有误，也会让 exp 看起来“提前失效”。

3. refresh token 已经过期或没生效。 业务代码里自动续签失败，页面继续拿旧 access token 请求接口，就会不断 401。

4. 本地缓存里混入旧 token。 多环境切换、本地存储没清、标签页保留了旧状态，都可能把无效 token 继续发给接口。

一套够用的排查顺序

  1. 先把 token 解码，确认 payload 能正常读出来。
  2. 对照当前时间看 exp 是否已经过去，不要只看接口报错文案。
  3. 如果看起来“没过期”，再检查浏览器系统时间、服务端时区和 NTP 同步。
  4. 继续确认是否有 refresh 流程，以及 refresh 请求是不是被拦截、失效或循环失败。
  5. 最后清理 localStorage、sessionStorage、cookie 和多标签页状态，排除旧 token 污染。

两个很容易误判的点

“解码成功”不等于“签名有效”

JWT 工具能帮你看清 header 和 payload，但不会替你验证服务端密钥是否匹配。 所以解码能看见内容，只说明格式像 JWT，不代表签名一定可信。

“接口 401”也不一定全是过期

权限范围不够、用户被封禁、资源不存在、网关把 token 剥掉，都可能返回类似的错误。 先看 payload，再结合后端日志，判断才会更准。

快速结论

遇到 JWT 过期问题，最有效的方法不是盲目重新登录，而是先看清 token 本身的时间字段，再检查刷新链路和本地缓存。 如果你只是想快速确认这枚 token 什么时候签发、什么时候过期，可以直接打开 Tools321 的 JWT 工具 做第一轮判断。
